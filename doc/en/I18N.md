# I18N.md — Multilingual architecture of Teclatlon

> 🌐 **Other languages:** [Español](../es/I18N.md)

Technical reference for the internationalization system (`App.i18n`)
and a step-by-step recipe for adding a new language. Read it together
with [`SPEC.md` §6](SPEC.md) (language policy) and
[`technical.md` §3](technical.md) (technical integration).

**Current status**: Spanish (`es`, default and source of truth) and
English (`en`). The system is **designed to support more than two
languages**, but today it has several binary `es`/`en` spots (number
format, numpad step expressions, language selector, parity validator)
that must be generalized before adding a third — see §4.

---

## 0. Language policy (summary)

- **Multilingual UI**: every user-visible text exists in each supported
  language (`es`, `en`, …).
- **Technical code is always English**: variable names, functions,
  JavaScript objects and — **crucially, the keys of
  `strings.<locale>.js`** — are in English. Only the values are
  translatable UI text. This separation keeps `App.i18n.t('lessonName')`
  readable in source code regardless of the active language.

  ```js
  // ✅ Correct — key in English, values in the file's language
  // strings.es.js
  App.i18n.register({
    lessonName: 'Coloca los dedos',
    encouragement: '¡Casi! Inténtalo otra vez.'
  }, 'es');
  // strings.en.js
  App.i18n.register({
    lessonName: 'Place your fingers',
    encouragement: 'Almost! Try again.'
  }, 'en');
  ```

- **`es` is the default language and the source of truth when a key
  is missing** in another language. The Spanish fallback **hides the
  gap** on screen (it does not fail loudly), so **no supported
  language is ever left with a key without its translation** — before
  releasing a new language, every key in the base `strings.<locale>.js`
  has its translated equivalent. `scripts/check.js` helps detect
  drift (see §5, step 7).

## 1. Pieces of the system

```
assets/js/i18n.js          # Core: App.i18n (detection, persistence, t/pick/apply)
index.html                 # Inline "pre-paint" script (detect language before
                            # the CSS) + synchronous load of strings.es.js and
                            # strings.en.js
strings.es.js              # App root text in ES
strings.en.js              # App root text in EN
data.js                    # Practice data indexed by language
                            # ({ es: [...], en: [...] } in placement, lessons,
                            #  words, numpadSteps)
app.js                     # Uses App.i18n.t()/.pick()/.locale() to read text
legal/index.html           # Explicit language selector (2 fixed buttons)
legal/strings.es.js        # Legal page text in ES
legal/strings.en.js        # Legal page text in EN
assets/js/i18n.js          # Activatable locales catalog + core/feedback
                            # (already-registered keys: core.*, feedback.*)
scripts/check.js           # Key parity validation + sw.js/manifest check
sw.js                      # Caches strings.<locale>.js in ARCHIVOS
```

### 1.1 `assets/js/i18n.js` — core

```js
var CLAVE_LOCALE = 'teclatlon:locale';
var SOPORTADOS = ['es', 'en'];   // activatable languages
var POR_DEFECTO = 'es';          // fallback if a key is missing or the
                                // detected language is not supported
```

- **Detection** ([`detectar()`](assets/js/i18n.js), ~line 73): walks
  `navigator.languages`, keeps the 2-letter prefix of the first one
  that appears in `SOPORTADOS`. If none matches, returns `POR_DEFECTO`.
- **Persistence** (`locale()` / `setLocale()`): key
  `localStorage['teclatlon:locale']`. If a saved value is supported,
  it wins over detection. `setLocale()` saves and **reloads the page**
  (no in-place re-render).
- **`register(dict, locale)`** — multi-file signature (recommended):
  registers `dict` only in `locale`. If `locale` is not in `SOPORTADOS`,
  the call is silently ignored. Use it in all new
  `strings.<locale>.js`.
- **`register(dict)`** — legacy signature `{es:{...}, en:{...}}`:
  iterates over `SOPORTADOS` and registers the present locale's
  branch. Kept for backwards compatibility; do not use it in new files.
- **`t(key)`**: looks up `key` (dotted, e.g. `'core.back'` or
  `'feedback.success'`) in the active language. If missing, falls back
  to `POR_DEFECTO` (Spanish). If still missing, returns the `key`
  itself (so broken keys are visible on screen). If the value is an
  array, joins it with `', '` (intended for debugging, not UI).
- **`pick(key)`**: like `t`, but for keys whose value is an **array**
  of variants (e.g. `feedback.success`) — returns one at random. Used
  by `app.js` for success/encourage messages.
- **`apply(root)`**: applies `data-i18n` (→ `textContent`) and
  `data-i18n-aria` (→ `aria-label`) to every node under `root`
  (default `document`). Runs itself on `DOMContentLoaded`. Also sets
  `document.documentElement.lang` and, if `<html>` has
  `data-i18n-title="key"`, sets `document.title = t(key) +
  ' | Teclatlon'`.
- **`lang()`**: `'en' → 'en-US'`, anything else → `'es-ES'` (binary
  today — see §4). Used by `App.tts.speak()` to pick the
  `speechSynthesis` voice.

### 1.2 Common keys (`core.*`, `feedback.*`)

Defined once in `i18n.js`, **do not redefine** in the app's
`strings.<locale>.js`. All subkeys are in English (technical code):

| Key | ES | EN |
|---|---|---|
| `core.back` | ← Volver | ← Back |
| `core.understood` | Entendido | Got it |
| `core.listen` | 🔊 Escuchar | 🔊 Listen |
| `core.listenInstructions` | Escuchar las instrucciones | Listen to the instructions |
| `core.listenText` | Escuchar el texto | Listen to the text |
| `core.rest` | ¡Llevas un buen rato! Puedes descansar si quieres. | You have been playing a while! You can rest if you want. |
| `core.dataProtection` | Teclatlon no recolecta datos | Teclatlon does not collect data |
| `feedback.success` (array) | ¡Muy bien! / ¡Genial! / … | Well done! / Great! / … |
| `feedback.encourage` (array) | Casi. ¡Inténtalo otra vez! / … | Almost. Try again! / … |

### 1.3 App `strings.<locale>.js`

Pattern (see [`strings.es.js`](strings.es.js) as the gold reference):

```js
/* strings.es.js */
(function () {
  'use strict';

  App.i18n.register({
    title: '⌨️ Teclatlon',
    textoNombre: '¿Cómo te llamas?',
    // ... rest of ES keys
    dedo: {
      lp: { mano: 'mano izquierda', nombre: 'meñique' },
      // ... rest of fingers
    },
    teclaLabel: { espacio: 'espacio', borrar: 'borrar' }
  }, 'es');
})();
```

```js
/* strings.en.js */
(function () {
  'use strict';

  App.i18n.register({
    title: '⌨️ Teclatlon',
    textoNombre: 'What is your name?',
    // ... rest of EN keys
    dedo: {
      lp: { mano: 'left hand', nombre: 'pinky' },
      // ... rest of fingers
    },
    teclaLabel: { espacio: 'space', borrar: 'delete' }
  }, 'en');
})();
```

**Important**:

- **Keys are technical code and always in English**, regardless of the
  UI language. Only the values are translatable.
- The `title` key must always exist (used by `data-i18n-title` for the
  `<title>`).
- **Keys must match exactly** between `strings.es.js` and
  `strings.en.js` (verified by `scripts/check.js` §2). If you add a
  third language, its keys must also match the base pair.
- **Nested objects work as namespaces**: `dedo: { lp: {...} }` is read
  with `t('dedo.lp.mano')`. The `clavesPlanas()` function in
  `scripts/check.js` flattens keys for parity comparison.
- **Brace placeholders** (`'{n} times'`) are substituted manually in
  `app.js` with `.replace('{n}', value)`. If the same placeholder
  repeats twice in a key, use `.replace(/\{n\}/g, value)`.
- **Never use an array when you need to index by position** (`t()`
  joins the array with commas). For tables indexed by number, use an
  object with text keys: `{ 0: '', 1: 'miles', 2: 'millones' }`.
- **Only the common keys** (`core.*`, `feedback.*`) live in
  `i18n.js`. Anything else lives in the app's `strings.<locale>.js`
  (or in `legal/strings.<locale>.js`).

### 1.4 `data.js` — per-locale arrays

Practice content (lessons, words, numpad steps, placement) is indexed
by locale:

```js
DATA.placement = { es: [...], en: [...] };
DATA.lessons    = { es: [...], en: [...] };
DATA.words      = { es: [...], en: [...] };
DATA.numpadSteps = { es: [...], en: [...] };
```

For each `field`, `app.js` reads with `DATA.<field>[App.i18n.locale()]`.
The per-locale arrays **must exist in every supported locale** — if
you add a language, copy the base pair array (English or Spanish) as
a starting point and adapt it. Don't literally translate lists of
words or phrases that have cultural or pedagogical clashes (see §3).

### 1.5 HTML: `data-i18n*` attributes

```html
<html lang="es" data-i18n-title="title">
...
<h1 data-i18n="title">⌨️ Teclatlon</h1>
<button data-i18n-aria="core.listenInstructions" aria-label="Escuchar las instrucciones">🔊</button>
```

The Spanish text/`aria-label` stays as the default HTML content (so the
page makes sense even if `i18n.js` fails to load) and `apply()`
overwrites it on startup. Attributes `apply()` does **not** cover
(set manually in `app.js`): `placeholder` on `<textarea>`/`<input>`.

### 1.6 Script load order (mandatory)

```html
<script src="assets/js/utils.js"></script>
<script src="assets/js/i18n.js"></script>
<script src="assets/js/tts.js"></script>
<script src="assets/js/storage.js"></script>
<script src="assets/js/feedback.js"></script>
<!-- Both locale files load synchronously, no document.write -->
<script src="strings.es.js"></script>
<script src="strings.en.js"></script>
<script src="data.js"></script>
<script src="app.js"></script>
```

`i18n.js` loads before `tts.js`/`feedback.js` (both read the active
language). The two `strings.<locale>.js` files load synchronously
**before** `data.js` and `app.js`, so `App.i18n.register` has already
populated the dictionary when any UI code calls `App.i18n.t()`.
**`document.write` is not used** (modern browsers process
`document.write`-injected `<script>` tags asynchronously, which would
leak literal keys into the DOM during the initial render).

### 1.7 Pre-paint bootstrap (inline in `<head>`)

[`index.html`](index.html) carries an inline `<script>` in `<head>`
that duplicates `i18n.js#detectar()` and sets `<html lang="...">` and
`data-locale` before the stylesheet loads. This script must **stay in
sync** with `i18n.js`: if you add a language, update **both**
`SOPORTADOS` arrays and the inline `detectarIdioma` function (see §4
and §5 step 1).

### 1.8 Language selector

The visible selector lives in two places:

- **Main app** (`index.html`, inside the sliding settings drawer
  `#drawerAjustes`): an "Idioma" row with `.btn-idioma` buttons, one
  per language. The listener is wired in `app.js` and calls
  `App.i18n.setLocale('es' | 'en')`.
- **Legal page** (`legal/index.html`): an explicit, always-visible
  selector with two fixed `<button>` elements (`#btnIdiomaEs`,
  `#btnIdiomaEn`), `aria-pressed` reflected by a
  `pintarSelectorIdioma()` function.

In both cases, the buttons **are not generated from `SOPORTADOS`** —
they are fixed in the HTML. Adding a language means adding a button by
hand in both places (see §5).

## 2. Number format and numpad expressions: it's NOT just translation

The app has a **number-pad game** and a **free-writing mode** that
reads back what was typed. These two points are the most delicate part
of the system — translating the word without touching the format
produces a number or expression that reads wrong or flat-out false:

- **Thousand/decimal separators**: Spanish uses `.` for thousands and
  `,` for decimals (`1.234,50`); English is the other way around
  (`1,234.50`). Even though the app doesn't currently display formatted
  amounts, any future extension (PPM panel, metrics) must branch per
  language, not literally translate the separator.
- **Number scale**: Spanish uses the long scale (10⁹ = "mil millones",
  10¹² = "un billón"); English uses the short scale (10⁹ = "one
  billion", 10¹² = "one trillion"). Translating "billón" as "billion"
  yields a number **a thousand times smaller** than intended. The
  `DATA.numpadSteps` array (num-pad steps) is a good place for each
  language to have its own readings if the number warrants it.
- **Numpad expressions**: "y pico", "más o menos", "una decena" are
  not literal translations of "and a bit", "more or less", "about ten"
  into English-natural English. Each language needs its own array of
  phrases in `strings.<locale>.js` (or `data.js`), not a translated copy
  of the base pair's list.

**General rule**: before literally translating any text that contains
a number, a date, a time or a currency, check how a native speaker of
the target language would actually say it. If needed, the template may
have a different sentence structure per language (see `core.listenText`
— no phrase in the current version, but the rule applies to
extensions).

## 3. Cultural content (lessons, words, phrases): do NOT translate literally

A rule as strict as §2, but for text instead of numbers: **a lesson,
a word or a phrase translated word-for-word from Spanish may lose its
pedagogical sense in the target language** — the example falls flat,
the word isn't used that way, the phrase sounds forced. The version in
each language must be **content native to that language**, with the
same difficulty and pedagogical intent as the original, not a
translation of it.

- **`DATA.lessons.<locale>`**: each lesson is a collection of
  characters to practice. The character list changes very little
  between languages (only `ñ` in Spanish, `ñ` in Asturian, etc.), but
  the introductory phrase or the transfer does.
- **`DATA.words.<locale>`**: the words game uses everyday nouns of
  the language ("gato", "casa", "nube" in Spanish — "cat", "house",
  "cloud" in English). Each language must have **its own vocabulary**
  with everyday words at the relevant level, not literal translations.
- **`DATA.numpadSteps.<locale>`**: the numpad readings (§2) are
  genuinely language-native content, not translations.
- **`textoNombre` and the "include my name" prompt**: each language
  writes the invitation and the model answer ("Me llamo María" →
  "My name is Mary") without depending on the Spanish string.

## 4. Binary `es`/`en` spots (to generalize when adding a language)

Reference grep: `grep -rn "locale() === 'en'" assets/`.

| File:line | What it does | What to change for a 3rd language |
|---|---|---|
| `assets/js/i18n.js:23` (`SOPORTADOS`) | `var SOPORTADOS = ['es', 'en'];` | Add the code: `['es', 'en', 'fr']` |
| `assets/js/i18n.js:91` (`lang()`) | `return locale() === 'en' ? 'en-US' : 'es-ES';` | Convert to a map `{es:'es-ES', en:'en-US', fr:'fr-FR'}` with fallback to `POR_DEFECTO` |
| `index.html` (inline script in `<head>`) | `var SOPORTADOS = ['es', 'en'];` and duplicated `detectar()` | Sync with `i18n.js` (same array, same function) |
| `index.html` (settings panel) | `.btn-idioma` buttons wired in `app.js` | Add a third button + listener in `app.js` |
| `legal/index.html` | 2 fixed buttons (`#btnIdiomaEs`, `#btnIdiomaEn`) + `pintarSelectorIdioma()` | Add a third button + entry in `pintarSelectorIdioma()` |
| `scripts/check.js` (parity `compararEsEn`) | Only compares `es`↔`en` | Generalize to N locales using `STRING_LOCALES` (see §5, step 7) |
| `sw.js#ARCHIVOS` | Lists `strings.es.js`, `strings.en.js`, `legal/strings.es.js`, `legal/strings.en.js` | Add `./strings.<xx>.js` and `./legal/strings.<xx>.js` |
| `sw.js#VERSION` | `var VERSION = 'teclatlon-v5';` | Bump the version to force re-download |
| `data.js` (per-locale arrays) | `placement`, `lessons`, `words`, `numpadSteps` only have `es`/`en` | Add the new language's key to each object |

## 5. Recipe: adding a new language (example: French, `fr`)

Execute in this order. Each step is mechanical except step 4 (content)
and step 5 (numbers/times).

### Step 1 — Register the language in the core

In `assets/js/i18n.js`:

```js
var SOPORTADOS = ['es', 'en', 'fr'];
```

And in the `lang()` map (binary today, see §4):

```js
var BCP47 = { es: 'es-ES', en: 'en-US', fr: 'fr-FR' };
function lang() { return BCP47[locale()] || BCP47[POR_DEFECTO]; }
```

Sync the inline script in [`index.html`](index.html) `<head>`: same
`SOPORTADOS`, same `detectarIdioma()` function.

### Step 2 — Language selector in the app and in `legal/`

**Main app** (`index.html`): add a third `.btn-idioma` button inside
the settings drawer `#drawerAjustes`, with `data-locale="fr"` and
visible text in French. Wire it in `app.js` the same way as the
existing buttons (`App.i18n.setLocale('fr')`).

**Legal page** (`legal/index.html`): add a third button in the visible
selector, e.g.:

```html
<button id="btnIdiomaFr" data-locale="fr" aria-pressed="false">🇫🇷 Français</button>
```

and update `pintarSelectorIdioma()` to reflect `aria-pressed` on the
new button too.

### Step 3 — `strings.fr.js` in the app

Create `strings.fr.js` (at the repo root) with the **same keys** as
`strings.es.js` / `strings.en.js`, keeping the same key names and the
same nested structure. Pattern:

```js
(function () {
  'use strict';

  App.i18n.register({
    title: '⌨️ Teclatlon',
    textoNombre: 'Comment tu t’appelles ?',
    // ... rest of keys translated to French
    dedo: {
      lp: { mano: 'main gauche', nombre: 'auriculaire' },
      // ... rest of fingers
    },
    teclaLabel: { espacio: 'espace', borrar: 'effacer' }
  }, 'fr');
})();
```

### Step 4 — `legal/strings.fr.js`

Create `legal/strings.fr.js` with the **same keys** as
`legal/strings.es.js` and `legal/strings.en.js`, registered with
`App.i18n.register({...}, 'fr')`.

### Step 5 — `data.js`: add the locale to each per-locale array

For each `DATA.<field>` indexed by locale, add the `fr` key with its
own content (not a literal translation of the base pair — see §3):

```js
DATA.placement   = { es: [...], en: [...], fr: [...] };
DATA.lessons     = { es: [...], en: [...], fr: [...] };
DATA.words       = { es: [...], en: [...], fr: [...] };
DATA.numpadSteps = { es: [...], en: [...], fr: [...] };
```

If you don't want to translate a specific field (e.g. `placement`
which is just coordinates), copy the base pair array as-is and answer
explicitly in the PR — explicit fallback is better than a forgotten
array, but the rule is: **every activated locale has its own content
in every array**.

### Step 6 — `sw.js` and `scripts/check.js`

Bump `VERSION` in `sw.js` (`var VERSION = 'teclatlon-v6';`) and add
the two new files to the `ARCHIVOS` array:

```js
'./strings.fr.js',
'./legal/strings.fr.js',
```

In `scripts/check.js`, generalize check #2 (`compararEsEn`) so it
compares **all active locales** of the base pair against the new one.
The cleanest form is to introduce a list of validated locales:

```js
var STRING_LOCALES = ['es', 'en', 'fr'];   // 'es' first = source of truth
```

and rewrite `compararEsEn(dir, etiqueta)` as
`compararLocales(dir, etiqueta, locales)` that verifies parity
between `es` and each declared locale. The `extraerDictDeStrings`
function already accepts any locale (it reads
`App.i18n.register({...}, loc)`), so that part doesn't need touching.

### Step 7 — Verify key parity

```bash
node scripts/check.js
```

`scripts/check.js` must list **zero failures**. If any key is missing
in `fr`, the check reports it in detail ("only in es", "only in fr").
**Don't ship with untranslated keys** — the Spanish fallback hides the
gap instead of failing loudly (§0).

### Step 8 — Functional verification

- **Main app**: changing the language from the settings panel (step 2)
  reloads the page and the interface appears in French. The choice
  persists in `localStorage['teclatlon:locale']`.
- **Legal page**: the explicit selector works the same way and the
  URL keeps the choice (`teclatlon:locale`).
- **Every screen**: every lesson, word, numpad step, closing
  celebration, `feedback.success` / `feedback.encourage` message,
  `aria-label` attribute and `<title>` appears in French. If any key
  is left untranslated, the literal key code shows on screen (this is
  intentional, see `t()` in §1.1).
- **TTS**: pressing 🔊, `App.tts.speak()` picks the voice with
  `lang()` (which now returns `'fr-FR'`); check that a French voice
  exists on the OS (if not, it falls back to the browser default voice
  — expected behaviour, not a bug).
- **Service worker**: with the PWA installed, open the app and check
  that `strings.fr.js` loads (browser network panel, filter
  `strings`).

## 6. What NOT to do

- **Don't trust machine translation for numbers, dates, times or
  currency** without checking the target language's real convention
  (§2 and step 5).
- **Don't leave a key without its equivalent in every supported
  language** — the Spanish fallback hides the gap instead of failing
  loudly. Even though the fallback works, it's considered incomplete
  and blocks the release.
- **Don't use arrays in `strings.<locale>.js` for data indexed by
  position/number** (`t()` flattens them with `join(', ')`); use a
  text-keyed object (`{0:'', 1:'...'}`).
- **Don't add a new language without first generalizing the binary
  `es`/`en` spots from §4** — otherwise the new language will silently
  inherit English (or Spanish) behaviour for number format (`lang()`),
  detection (`detectar()`), the validator (`check.js`) and the service
  worker (`sw.js`).
- **Don't literally translate lessons, words, idioms or any text that
  depends on a pun, a rhyme or a cultural reference** — write
  language-native content with the same difficulty and pedagogical
  intent (§3).
- **Don't load `strings.<locale>.js` with `document.write`**: Chrome
  and Firefox process `document.write`-injected `<script>` tags
  asynchronously, which would leak literal keys into the DOM during
  the initial render. Always use synchronous `<script src="...">` in
  `index.html` / `legal/index.html`.
- **Don't delete `strings.es.js` or `strings.en.js` when adding a new
  language** — they are the base pair and the source of truth (§0).
  The service worker caches them in `ARCHIVOS`; any change to cached
  files requires bumping `VERSION` (`'teclatlon-vN'`) to force the
  re-download in installed PWAs.
